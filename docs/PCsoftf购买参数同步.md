# PCsoftf 购买参数同步

本次功能属于 PCsoftf 分支。使用配套的 `DF_PlayClick_Server_Qt_PCsoftf.exe` 和 `DF_PlayClick_Client_Qt_PCsoftf.exe`。

## 服务端

- 总览页按确认的预览排列：购买参数、执行参数、客户端同步状态、底部状态及完整日志。
- 购买款式单选 1～5。每款独立保存子弹名称和购买阈值，切换款式不会丢失其他款的内容。
- 购买方式使用 Qt 提供的四种选项，可选择原来的方式。原生最低价方式不写入禁用的阈值，服务端继续记忆该数值。
- 下拉选项来自已绑定的实际 Qt 窗口，连接或重新绑定时读取五款列表；离线显示最近一次读取的缓存，不内置示例子弹。
- 不同客户端的列表不一致时，服务端提供共同支持的选项。各目标还会分别验证是否支持当前选择。
- 配置保存在服务端同目录 `DF_PlayClick_Server.ini` 的 `AuctionPurchase` 节。
- 总览显示本次期望配置及逐客户端同步结果；原有金额、收益、上架与准备信息保留在“客户端列表”页。监听、调度设置和统计保留在“日志与状态”页。
- 缩小窗口时，上方内容可滚动，底部日志仍然可见。

## 应用时机及核对

1. 仅向已绑定 `AuctionQtControl.exe` 的币号及老板同步。
2. 客户端空闲时应用；执行中保留当前参数，等本轮结束后应用最后一次修改。
3. 在目标 Qt 取消其他四款勾选，启用指定款，写入所选购买方式、子弹及允许编辑的阈值。
4. 逐项回读。服务端只在收到对应版本的成功回报后显示“已同步”；未回报、旧回报及失败回报不会被当作成功。
5. 更换绑定窗口会重新读取列表。断线、停止及关闭时清理旧任务，避免旧结果写回新连接。

UI Automation 负责读取、复选框切换及文本写入。Qt 6 的界面树可能省略弹窗视口外的条目，因此从首尾检查并按重叠页面读取完整列表，缓存每页名称，保留原有顺序；读取不提交选择。同步选择时向目标 HWND 的关闭状态下拉框定向发送滚轮消息，逐次回读直到目标值，不展开列表，也不使用全局键鼠输入、`SetForegroundWindow` 或 `SetFocus`。绑定时首次读取完整选项仍需要临时展开列表；随后使用缓存，服务端修改子弹和购买方式时不展开。展开、收起和滚动过渡有等待与检查，读取失败时不把截断列表当作成功。

## 验证

使用仓库的 `build_qt_release.ps1` 构建。以下测试在已构建并映射 P:/Q: 的环境中执行：

```powershell
python Tests/RunAuctionPurchaseRuntimeTests.py
python Tests/RunServerPurchaseSyncTests.py
python Tests/VerifyServerPurchaseUi.py
python Tests/RunAuctionControllerRuntimeTests.py
```

前两项使用隔离的 Qt 窗口和回环连接，检查真实 UIA 控件、单选、每款记忆、模式切回、执行中延后应用、停止、快速重新绑定和协议回报。参数自动化测试在独立 Windows 测试桌面上运行，避免物理鼠标关闭测试弹窗；覆盖 82 项长列表的逐项顺序、末尾选项写入及读取不改变选择。原有按钮执行状态机另做回归。

界面对照以确认预览的 1018×1196 尺寸为基准，比较八个关键区域，允许原生整数像素布局与浏览器小数布局之间最多 1px 的差异。窗口控制按钮和文字栅格化使用原生 Qt/Windows 绘制，不做整图逐像素相等的承诺。截图及几何对照结果保存在 `build/server-purchase-runtime/`。

测试不会调用真实交易程序的购买或上架按钮。真实交易程序的下拉列表读取另行验证，并检查读取前后的选择未发生变化。

本次修复：主界面增加独立执行回报列，保留最近一次执行成功或失败的原因；币号在调用前发现所需按钮不可用时立即回报失败，调用后的不可用状态仍按正常执行中等待。针对本次变更仅运行状态机、回报显示和后台切换验证（`RunAuctionPurchaseRuntimeTests.py --focused`），无需重复整套 UI 对照。

补充后台切换兼容：有些目标控件忽略滚轮消息。首次绑定读取目录时缓存各下拉弹窗 HWND；滚轮切换无效时，在弹窗未显示前临时设置透明及不激活样式，通过原有按键选择并回读。收起后恢复原样式。缓存失效时提示重新绑定，不直接显示弹窗。针对忽略滚轮的 Qt 控件验证了正向切换、反向切回、阈值写入和透明弹窗；本次未调用真实交易按钮。

Qt 全自动闭环：仅在全自动执行开启、币号仍处于本轮执行且已准备时，收到执行成功回报后清除执行锁，直接下发带独立 requestId 的下一轮上架请求。Qt 上架不依赖旧游戏 OCR 文本和价格。收到上架成功后沿用原组数及老板准备判断再次自动执行。关闭全自动、执行失败、停止后的迟到回报不触发下一轮；重复执行成功回报不清除已开始的上架任务。首次仍需先建立币号上架成功和老板准备成功状态。使用 RunServerPurchaseSyncTests.py --qt-auto-relist 验证了连续两轮、重复回报、关闭全自动、失败停止及非 Qt 参数校验。
